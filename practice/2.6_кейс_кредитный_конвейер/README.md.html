Кредитный конвейер: от первого запроса до панели в BI

Скачать README.mdНа GitHub

Работаете на общем стенде? БД bank_training уже залита, Metabase поднят общий. В тетради откройте, Restart Kernel → Run All. В редакторе SQL Metabase не забудьте выбрать базу «Учебная база банка» (Sample Database — это встроенная H2, там нужных таблиц нет). Общие шаги стенда — в ../_STAND.md.

Управленческий вопрос. Где конвейер теряет время и заявки — и что исправлять в первую очередь?

Работаем только запросами. Pandas в этом кейсе не нужен: проверка данных, чистка и расчёт делаются на SQL, и тот же SQL потом уезжает в панель BI без переписывания.

Что в папке

Файл Зачем
конвейер_sql.ipynb тетрадь целиком: осмотр данных → проверки → чистый слой → расчёты → запрос для панели
разведочный_анализ.ipynb что такое очистка данных и какие решения принимаются по данным; с графиками
памятка_sql_pandas.ipynb одна операция двумя способами: запрос и pandas, со сверкой результатов

Данные лежат в базе стенда, выгрузки-исходники — в data/pipeline/.

Порядок чтения: сначала разведочный_анализ.ipynb — там разбирается сам метод (что чистим, почему медиана вместо среднего, как читать распределение), потом конвейер_sql.ipynb — там тот же материал доводится до панели в BI.

Что в базе

Четыре выгрузки, как они приходят из систем:

Таблица Что в ней Строк
raw_applications заявки: продукт, канал, регион, сумма, время подачи 3 672

Период — с января по август, все данные синтетические.

Как провести

1. Осмотр. Сколько строк, какие границы периода, как распределены заявки по каналам. Первый запрос к незнакомым данным всегда про объём и границы.

2. Четыре проверки до расчётов. Повторы строк (72 лишних), служебные записи (58 тестовых заявок), невозможные значения (171 событие, где этап закончился раньше, чем начался) и разрывы между источниками (54 заявки без решения).

3. Цена пропущенной проверки. Конверсия в выдачу «как есть» — 49,6 %, после отсева повторов и тестовых — 51,4 %. Почти два процентных пункта на пустом месте; это тот аргумент, ради которого стоит показать проверки до расчётов.

4. Чистый слой представлениями. v_applications_clean и v_stage_events_clean: правило чистки живёт в одном месте, а не копируется в каждый запрос.

5. Расчёты. Куда доходят заявки, сколько времени занимает этап (медиана и P90, потому что среднее по длительностям обманывает), где теряются заявки.

6. Запрос в панель. Итоговый SQL — срок этапа в разрезе канала — оформляется представлением v_pipeline_stage_sla и вручную переносится новой панелью в систему дашбордов. Порядок шагов интерфейса — в конце тетради.

Проверка

Стенд поднят и в таблицах ровно столько строк, сколько должно быть:

./run.sh status

Тетрадь исполняется от начала до конца на чистом стенде — это и есть критерий готовности кейса. Числа в таблицах выше воспроизводятся её запросами.
